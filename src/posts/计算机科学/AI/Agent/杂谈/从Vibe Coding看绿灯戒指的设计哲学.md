# 从Vibe Coding看<span style="font-weight: bold; color: green;">绿灯戒指</span>的设计哲学

> [!TIP]
>
> - 哈尔·乔丹：“我心里想得出什么，就能创造出什么——只要我集中意志。”
> - 约翰·斯图尔特：“<span style="font-weight: bold; color: green;">戒指</span>成就不了灯侠，是灯侠成就了<span style="font-weight: bold; color: green;">戒指</span>。”
> - 凯尔·雷纳：“<span style="font-weight: bold; color: green;">戒指</span>只受想象力的限制。”

如果你看过[<span style="font-weight: bold; color: green;">《绿灯军团》</span>](https://movie.douban.com/subject/36225837/)，你一定记得那个画面：一枚小小的<span style="font-weight: bold; color: green;">绿灯戒指</span>套上手指，绿光一闪，心里想到什么，手上就出现什么。最近我也在看这部电影，主角们说的话让我醍醐灌顶——<span style="font-weight: bold; color: green;">绿灯戒指</span>被称为宇宙中最强大的武器之一，但它的力量从来不来自<span style="font-weight: bold; color: green;">戒指</span>本身，而来自佩戴者的**意志**。

<!-- more -->

`Vibe Coding` 实际上也是和绿灯戒指类似的东西：`AI` 成就不了程序员，是程序员成就 `AI`。`Vibe Coding` 这个词的发明者 `Andrej Karpathy` 说，这是一种“完全交出代码控制权”的玩法——不读 `diff`，报错就原样丢回模型，直到程序“差不多能用”。任何一个人打开 `Cursor` 的那一刻，都会面临两个和灯侠一模一样的问题：**你有多清楚自己要什么**，以及**你愿不愿意为生成出来的代码负责**。

这两个问题，在漫画里叫“意志”和“恐惧”，在编程里叫“需求定义”和“代码审查”。

------

## 一、<span style="font-weight: bold; color: green;">戒指</span>不给你意志，它只放大意志

哈尔·乔丹的台词是整个绿灯设定的地基：“我心里想得出什么，就能创造出什么——只要我集中意志。”

注意后半句。**“集中意志”不是蛮力，是清晰的意图。** 哈尔能造出巨型机甲、精密仪器，不是因为他力气大，而是因为他脑子里有那个东西的完整图像。同样一枚戒指，戴在不同的人手上，效果天差地别——漫画里，盖伊·加德纳被腰斩之后，硬是靠着戒指重组了自己的整个身体。那场戏里戒指没有变得更强大，强大的是盖伊不肯死的意志。

放到 `Vibe Coding` 里，这句话翻译过来就是：**AI 只会放大你的能力，不会凭空替你制造能力。**

你让 AI 做一个“帮用户记账的工具”，和让它做“一个能让用户在三秒内完成记账、自动生成月度消费洞察、还能在预算超支时提醒的工具”，产出的东西天差地别。前者是 AI 的平均水平，后者才叫产品。那篇流传很广的文章说得更直接：**如果你什么都没有，AI 放大的可能只是你的混乱。**

------

## 二、<span style="font-weight: bold; color: green;">绿灯侠</span>无法想象出自己不知道的东西

凯尔·雷纳说“戒指只受想象力的限制”。这句话藏着一个很少有人注意的前提：**想象力本身也是有边界的，它的边界就是知识。**

约翰·斯图尔特是建筑师出身，他的灯戒造物永远有结构感、有承重逻辑。漫画里有一个经典例子：他是在看完了盾构机的图纸之后，才用灯戒创造出了盾构机。在那之前，灯戒能捏出来的只有他脑子里已有的东西——没有图纸，就没有造物。

绿灯军团的设定里，戒指内置了庞大的知识库，军团里还有数不清的图纸供灯侠学习。`AI` 其实一模一样：`GitHub Copilot` 之所以强大，正是因为它检索了 `GitHub` 上大量的开源代码、学尽了语法模式。**灯戒的知识库来自军团，AI 的知识库来自开源世界——但最终决定你能造出什么的，永远是你自己装进脑子里的那一份。**

这就是为什么 `Vibe Coding` 的坑，只有懂行的人才能看出来。

比如，AI 非常容易写出 `if (status == "XXX")` 这样的代码。行业内管这叫**魔法数**——判断语句直接硬编码一个字符串或整数值。正确做法是：判断只依赖常量和枚举，其他的一律不允许。如果你没有系统学过计算机、没有亲手写过代码，你甚至不知道这行代码有问题。坑已经埋下了，你却看不出来。

还有经典的 `try catch` 层层嵌套，AI 喜欢过度优化，AI 的“记忆问题”……等你学了，你就知道，都是坑。

所以：灯侠造不出他不知道的东西，Vibe Coder 也审不出他看不懂的代码。**AI 不会替你发现坑，因为你根本无法指出问题在哪里。** 这样的代码不会自己消失，只会越来越难维护。

------

## 三、三种用<span style="font-weight: bold; color: green;">戒指</span>的方式，也是三种 Vibe Coder 的姿态

在《从亲密关系看Git合并与冲突的设计哲学》那篇里，我用 `Git` 的三种冲突解决方式讲过三种爱的姿态。巧的是，面对一枚绿灯戒指，漫画里也出现过三种用法，每一种都对应着 `Vibe Coding` 里的一种姿态。

### 1. 把意志交给<span style="font-weight: bold; color: green;">戒指</span>（全盘接受 AI）

这是 `Vibe Coding` 最原始的定义：不读 `diff`，报错原样丢回模型，直到“差不多能用”。这对应 `Git` 冲突面板里的 `Accept Incoming Change`——**全盘接受对方的输出，放弃自己的想法。**

风险是明摆着的：AI 生成得越快，你没看懂的代码积累得越快。魔法数、嵌套的 `try catch`、没人能解释的“看似能跑”的逻辑——最后你会变成“空心程序员”，仓库里全是 AI 的代码，没有一行你能说清楚它为什么存在。

适用场景：`Karpathy` 自己限定的范围——一次性的周末项目。错了能立刻删，失败成本清晰且很低。

风险：一旦把这种模式带进生产环境，出了事你连报错都解释不了。

### 2. 拒绝戴上<span style="font-weight: bold; color: green;">戒指</span>（坚持全部手写）

另一种极端：坚持所有代码都必须亲手敲，把 AI 拒于千里之外。这对应 `Git` 里的 `Accept Current Change`——**固执己见、拒绝让步。**

平心而论，开源世界里真的有人这么干，而且理由很硬：`Zig`、`OpenJDK` 直接禁止 AI 生成的代码进入仓库；`Linux` 内核要求 `Signed-off-by` 必须是人，AI 参与只能写进 `Assisted-by`。他们不是反技术，是反“无意志者举着戒指刷 PR”——**维护者要的是灯侠，不是 vibe bot。**

但对你个人而言，完全拒绝也有代价：时间会浪费在脚手架、样板代码、接口搬运和文档检索上。拒绝升级工作方式的开发者，输的不是手速，是时间。

适用场景：学习阶段。从来没有从零敲过代码的人，无法理解 AI 生成的代码——就像没经过训练的灯侠，连个稳定的光球都捏不稳。**跳过训练直接依赖戒指，等于把大楼建在别人的图纸上。**

### 3. 人戴<span style="font-weight: bold; color: green;">戒指</span>，人机共创

第三种方式，是绿灯军团的方式，也是 `Git` 在冲突面板里最推荐的方式（`Accept Both Change`）：**把两边的代码都留下来，融合成新的东西。**

灯侠戴着戒指，但决定造什么的是灯侠；AI 生成代码，但决定接受哪一行的是你。换句话说：**让模型扩大产出，让人保留解释、验证与决策权。** `Simon Willison` 给过一个实用边界：代码即使由模型生成，只要你审查、测试并能解释它，你依然是在做软件开发。

具体长什么样？拿魔法数来演一遍：

```text
// AI 生成的第一版：魔法数直接上场
if (status == "XXX") {
    // 不知道 XXX 是什么，以后也没人会知道
}

// 你提出约束：判断只依赖常量和枚举，重写并补上测试
// AI 重写后的第二版：
if (status == OrderStatus.CANCELLED) {
    // 语义清晰，可维护，可测试
}

// 最终版：你审查 diff、跑完测试、能解释每一行，才允许它进入仓库
```

这不是简单的“AI 写、你复制粘贴”，而是创造出一种比单干更好的工作方式：**AI 负责生成的速度，你负责方向的正确。**

适用场景：一切要上线给别人用的代码——涉及登录、权限、支付、密钥、数据库迁移的时候，解释权必须留在人手里。

好处：每一次成功的“人机合并”，你对系统的掌控力就上升一个台阶。因为你证明了：**你可以让 AI 跑得飞快，同时依然知道它为什么这么跑。**

判断自己此刻该用哪种姿态，只需要一个问题：

> **如果明天它出错，你能否解释发生了什么，并安全恢复？**
>
> 如果答案是否定的，今天就还没有完成开发。

------

## 四、恐惧：灯戒唯一的弱点

绿灯戒指的力量来自意志，而它唯一的弱点，是恐惧。

漫画里，恐惧是绿色的天敌：灯侠一旦陷入恐惧，光构就会颤抖、变暗，甚至彻底失效。所以绿灯军团挑选成员的第一个标准，从来不是力量，而是**“能够克服巨大恐惧”**。戒指从不奖励毫无恐惧的人，它奖励的是带着恐惧仍然敢举起手的人。

`Vibe Coding` 也是一样的。

如果你恐惧，如果你连自己的业务逻辑都搞不清楚，AI 也无法替你搞清楚。就算问题真的出现了，AI 也不会替你把它找出来——因为你自己根本无法指出问题在哪里。恐惧会让你把 AI 的输出原样收下、不敢质疑，也会让你把 AI 关在门外、不敢使用。前者让你在黑暗里狂奔，后者让你被时代抛下。

但还有一种恐惧藏得更深：**不敢看自己生成的代码。** 知道自己不懂，所以干脆不看——这才是 Vibe Coder 最危险的那一刻。

绿灯军团从来没有说过“意志强大的人就不再恐惧”，他们说的是“克服恐惧”。`Vibe Coding` 里真正的勇气，不是不用 AI，而是敢用 AI 之后，还敢逐行看完它写出来的每一行。

------

## 写在最后

`Vibe Coding` 和绿灯戒指，本质上是同一个**放大器模型**：

1. **意志决定造什么** —— 需求越清晰，产出越完整；AI 放大的是你的意图，不是替你产生意图。
2. **知识划定想象力的边界** —— 先有图纸，后有造物；先懂代码，才审得出代码里的坑。
3. **三种姿态对应三种命运** —— 依赖者被带进坑里，拒绝者被时代抛下，共创者让 AI 飞得更快。

戒指不会让你成为灯侠，它只会让已经是灯侠的人飞得更快。下次打开 `Cursor` 之前，不妨想想：你的意志足够集中吗？你的图纸准备好了吗？你敢不敢看它写出来的每一行？

> 白昼朗朗，黑夜茫茫。
> 魑魅魍魉，无所遁藏。
> 恶徒奸党，惧吾神光。
> 绿灯长明，万世光芒！

愿你的仓库里没有魔法数，愿你的戒指上只有意志。

>

>

>

>

>

>

>
> 你有产品思维，AI 会让你快十倍。你有审美，AI 会让你出图更快。你有技术基础，AI 会让你迭代更猛。你有商业判断，AI 会帮你快速验证。
>
> 但如果你什么都没有，AI 放大的可能只是你的混乱。
>
> AI 不是捷径，它只是把真正有执行力的人，送得更快。
