# SDK开发者的自我修养

> [!IMPORTANT]
>
> 随着软件项目的庞大，模块化开发成为必然，`高内聚低耦合`成为评价一个系统的重要标准。一个模块只做一件事，我们会把一些通用的代码分离出来，到其他项目中进行单独的维护，别人再通过依赖的方式使用。这就是SDK的作用。



**易用性与一致性**

- 遵循**最小惊奇原则**：接口行为应直观，符合开发者预期。使用者不需要去猜这个函数应该怎么用，如何传参，而是一眼就能看明白怎么用。
- 保持**命名风格统一**：类、方法、变量命名遵循平台惯例（如Java用CamelCase，Python用snake_case）。
- 提供**完整的错误处理机制**：定义清晰的异常/错误码体系，附带可读的错误消息。







**测试与质量保障**

- **单元测试覆盖率 ≥ 80%**，重点覆盖边界条件和异常路径。
- **集成测试**：模拟真实网络环境，测试端到端流程。
- **压力测试**：评估高并发下的性能和资源消耗。
- **持续集成（CI）**：每次提交自动运行测试、静态代码分析、构建检查。



## 一、 🔌 接口契约与向后兼容(最重要规范)

> [!NOTE]
>
> **一句话定义**：SDK 必须使用语义化版本号，并在同一主版本内严格遵守向后兼容承诺。

### 🌓 版本号即契约

> [!TIP]
>
> 所有对外暴露的接口（包括构造函数、方法签名、URL 路径、配置项）都必须在首次发布时确定版本号。

比如说针对 `Web API`，你可以用`/api/v2/users`方式定义`API`，这样不同版本可以共存，使用者可以逐步迁移，而不是被迫一次性全改。

#### ✍ 立刻上手: 使用`@since`文档注释

再比如说，我们的很多编程语言都有文档注释来标注函数或 API 的引入版本。以下是几个常见例子：

| 语言 / 工具                                  | 标签 / 写法                                 | 示例                                                         |
| -------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------ |
| **`Java` (`JavaDoc`)**                       | `@since`                                    | `/** @since 1.8 */`                                          |
| **`Python` (`Sphinx` / `reStructuredText`)** | `.. versionadded::`                         | `.. versionadded:: 3.6`                                      |
| **`C#` (`XML `文档注释)**                    | `<since>`                                   | `/// <since>4.0</since>`（非标准，常用 `<remarks>` 或自定义标签） |
| **`TypeScript` / `JavaScript` (`JSDoc`)**    | `@since`                                    | `/** @since 2.0.0 */`                                        |
| **`Rust` (`rustdoc`)**                       | `#![doc(html_root_url = "...")]` + 文本说明 | 通常写在注释中，例如 `/// Available since Rust 1.30.0.`      |
| **`Go` (`godoc`)**                           | 无专用标签，直接在注释中写明                | `// Since Go 1.12, this function does ...`                   |

**核心思路**：无论哪种语言，都推荐在文档注释中使用明确的标签或自然语言注明“**此功能从哪个版本开始可用**”。这有助于使用者快速判断兼容性。

拿我最熟悉的`kotlin`代码来举一个例子

在 `Kotlin` 的文档注释（`KDoc`）中，推荐使用 `@since` 标签来标明函数从哪个版本开始支持。这是从 `JavaDoc` 继承而来的标准做法，`Kotlin` 官方也遵循这一惯例。

**示例:**

```kotlin
/**
 * 对字符串进行某种处理。
 *
 * @param input 待处理的字符串
 * @return 处理后的结果
 * @since xxx组件名称 1.2.0
 */
fun processString(input: String): String {
    // ...
}
```

如果你编写的是 `Kotlin` 标准库级别的代码，也可以使用 `@SinceKotlin` 注解（如 `@SinceKotlin("1.2")`），标注这个API从什么`kotlin`版本开始支持，但这属于注解而非文档注释。文档注释中仍建议使用 `@since` 标签。

### 🌔 版本号语义化

版本号本身要传达含义，通常指遵循 `SemVer`（语义化版本） 规范，格式为 `主版本.次版本.补丁`：

- **主版本**递增：做了不向后兼容的改动（比如删了一个方法、改了参数类型）。使用者需要修改代码才能升级。
- **次版本**递增：新增了功能或接口，但旧代码依然能用。使用者可以放心升级。
- **补丁**递增：只修了 `bug`，没改任何外部行为。升级无风险。

#### 📃 举个例子说明版本语义化

假设你开发了一个短信发送 SDK，最初发布版本 `1.0.0`，有一个方法 `sendSms(phone, text)`。

- 后来你想增加一个 `sendVoiceCode(phone)` 的新功能，但不影响旧的 `sendSms` → 版本号升为 `1.1.0`（次版本+1）。使用者无需改代码就能享受新功能。
- 再后来你发现 `sendSms` 的参数顺序不合理，想改成 `sendSms(text, phone)` → 这是不兼容改动，版本号升为 `2.0.0`（主版本+1）。使用者必须手动调整调用代码。
- 如果只是修复了某个国际号码的编码 bug，没有任何接口变化 → 版本号升为 `1.1.1`（补丁+1）。使用者可以无缝升级。

### 🌕 主版本内的铁律

> [!IMPORTANT]
>
> 在同一个主版本下，不得以任何方式破坏调用方的现有代码。

这意味着：

- 所有对外暴露的接口都必须在首次发布时确定版本号(如使用`@since`文档注释)
- 不能删除或重命名已公开的类、方法、常量。
- 不能修改已有方法的参数列表、返回值类型或抛出的异常类型。
- 新增字段或方法时，必须确保旧代码不受影响（例如使用默认值、可选参数、重载方法而非修改签名），不能导致旧代码编译失败或运行出错。
- 返回结果只增不减（例如 `JSON` 响应中新增字段不影响旧解析器，除非对方严格校验 `schema`）。
- 废弃的接口必须保留至少一个次版本周期，并用 `@Deprecated` 等标注明确提示。
- 每次发布(`release`或发布到软件包仓库)必须更新版本号，并在变更日志中写明变更。

### 👩‍🔬 为什么接口契约如此重要

因为 `SDK` 是被无数下游项目依赖的“积木”，随意修改会导致下游崩溃。如果没有版本化和语义化，使用者无法知道升级会不会炸掉自己的代码，最终要么不敢升级，要么出问题后骂你。有了这套规则，双方都能轻松管理依赖关系。

一旦打破向后兼容，就必须提升主版本号。这是对使用者的基本尊重——让他们能够根据版本号判断升级风险，决定何时迁移。

### 🙅‍♀️ 反例

- 直接修改已有方法的参数类型而不升主版本；
- 将某个方法的返回值从 `String` 改为 `int`；
- 删除已公开的常量。删除了一个被大量引用的工具类。

## 最小惊奇原则: 一个好的设计是从一开始在设计层面就抹除使用者使用时的心智负担

**核心思想**：接口行为应直观，符合开发者直觉。使用者不需要去猜这个函数应该怎么用，无需查阅文档就能正确使用。

这句话其实就是唐纳德·诺曼那套"设计心理学"的另一种说法——**好的设计让东西自己会说话，坏的设计逼用户读说明书**。

好设计的标志其实是：**用户用完觉得"这玩意儿本来就该这样"，烂设计让用户觉得自己"怎么连这都不会用"**——锅其实是设计师的。

- 方法命名遵循行业惯例（如 `getXxx` 返回对象，`createXxx` 新建资源，`deleteXxx` 删除）。
- 参数顺序符合常识（如 `sendMessage(to, content)` 而非 `sendMessage(content, to)`）。
- 返回值类型一致且可预测（不要有时返回对象有时返回 null，考虑 Optional 或空集合）。
- 副作用最小化：查询方法不应修改状态；修改方法应有明确命名（如 `updateXxx`）。
- 避免隐式转换或魔法行为，例如自动重试、自动序列化等需在文档中明确说明。

提炼一下最小惊奇原则的精髓

> 💡 **惊奇感的来源 = 实际行为 − 用户预期**

- 差值为 0 → 零心智负担（理想态）
- 差值为正 → 意外之喜（但也可能是"咦？怎么会这样"的困惑）
- 差值为负 → 踩坑、报错、反直觉（最糟糕）

优秀的设计师做的不是"创造惊喜"，而是**把这个差值压缩到趋近于零**——让用户的所有预测都命中，所有动作都有预期内的结果。

这也是为什么"好的设计是透明的"：你感受不到它，因为你从来不需要去思考它。



##  最小依赖原则：零冗余依赖，不绑架使用者

- **规范**：SDK 运行时**只能依赖绝对必要的底层库**（如 JSON 解析、HTTP 客户端），且优先选择标准库或业界广泛使用的轻量库。
- **为什么**：每引入一个第三方依赖，就增加一层冲突风险、编译时间、包体积。
- **做法**： 
  - 列出所有依赖及其用途，定期审查是否有替代方案。 
  - 将可选功能（如特定序列化格式、日志后端）做成**可选依赖**（optional dependency），由使用者自行引入。
- **反例**：一个简单的 REST SDK 依赖了整个 Spring Boot Starter；一个纯计算 SDK 依赖了 Guava 只是为了用 `Preconditions`（完全可以用标准断言代替）。

## 错误即信息：统一异常/错误码体系

- **规范**：SDK 所有可预见的错误（网络超时、认证失败、参数非法）都应映射到**自定义异常类**或**结构化错误码**，并提供人类可读的消息和排查指引。
- **为什么**：调用方需要区分“重试”、“换参数”、“联系管理员”等不同行动。
- **做法**： 定义一个基础异常（如 `SdkException`），子类按类别划分（`AuthException`, `NetworkException`, `ValidationException`）。 错误码采用三段式：`[服务前缀]-[错误级别]-[序号]`，例如 `OSS-ERR-1001`。
- **反例**：直接抛出 `RuntimeException("error")`；返回 `-1` 表示所有失败。

## 配置集中且线程安全

- **规范**：所有可配置项（超时时间、重试次数、端点地址）应通过一个统一的配置对象或构建器传入，且**不可变**（immutable）或**线程安全**。
- **为什么**：多线程环境下配置被意外修改会导致诡异 Bug；分散的配置让使用者难以管理。
- **做法**： 使用 Builder 模式或 Config 类，构造完成后冻结。 提供合理的默认值（如超时 30 秒、重试 3 次），覆盖常见场景。
- **反例**：用全局静态变量控制超时；允许在 SDK 实例创建后修改配置。

##  日志可插拔：绝不强制绑定日志框架

- **规范**：SDK 内部的日志输出应通过**门面（Facade）** 接入，允许使用者替换为自己的日志实现（SLF4J、Log4j2、console 等）。
- **为什么**：强绑日志框架会导致项目中的日志配置混乱。
- **做法**： 使用语言标准的日志抽象（如 Java 的 SLF4J、Python 的 `logging`、Go 的 `log/slog`）。 提供关闭日志的选项（如设置日志级别为 OFF）。
- **反例**：直接在 SDK 里 `System.out.println` 或 `print()`；硬编码依赖 Logback。

##  测试与质量保障

**核心思想**：让调用方能轻松编写单元测试、集成测试，并在 CI 中稳定运行。

- **规范**：SDK 应内置**模拟服务器（Mock Server）** 或提供**测试桩（Stub）**，让使用者能在不依赖真实后端的情况下编写单元测试。
- **单元测试覆盖率 ≥ 80%**，重点覆盖边界条件和异常路径。
- **集成测试**：模拟真实网络环境，测试端到端流程。
- **压力测试**：评估高并发下的性能和资源消耗。
- **持续集成（CI）**：每次提交自动运行测试、静态代码分析、构建检查。
- **为什么**：开发者需要在 CI 中快速验证集成逻辑，不能每次都连生产环境。
- **做法**： 提供 `MockClient` 类，可预设返回值和延迟。 或者开放一个 `setBaseUrl` 方法指向本地测试服务器。
- **反例**：没有任何测试辅助工具，要求使用者自己 mock 整个 HTTP 层。

##  良好的文档和示例

README + API 文档 + 完整示例

- **规范**：每个 SDK 必须包含： 一个 README.md（安装、快速开始、链接到详细文档）。**API参考文档**：每个接口的参数、返回值、异常说明 。**迁移指南**：版本升级时的变更说明。 自动生成的 API 文档（如 Javadoc、godoc、typedoc）。 至少一个完整的“Hello World”示例代码，覆盖所有核心功能的使用示例，可直接复制运行，附带注释。
- **为什么**：使用者第一眼看到的就是文档，糟糕的文档等于产品死亡。
- **做法**： 示例代码放在 `examples/` 目录，并确保每次发布前能编译通过。 在 README 中列出常见问题（FAQ）和排错指南。
- **反例**：只有一个空 README；示例代码使用了过时的 API。



##  持续交付与发布流程

**核心思想**：自动化保证质量，语义化版本指导升级。

- **规范**：每次合并到主分支前必须通过： 单元测试覆盖率 ≥ 80% 静态代码扫描（检查依赖冲突、安全漏洞） 兼容性测试（用上一个版本的调用方代码跑一遍）
- **为什么**：人工审查容易遗漏回归问题，自动化才能保证质量。
- 版本号更新严格遵循 SemVer，禁止手动随意修改。
- **做法**： 在 CI 中配置 `breaking-change-detector` 工具。 发布时自动生成 CHANGELOG，并推送至包管理器（npm, Maven Central, PyPI 等）。
- **反例**：手动发布，忘记更新版本号；没有自动化测试，靠“感觉”判断是否兼容。
