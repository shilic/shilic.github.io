# SDK的CICD实践：用`release-please`实现自动化发布

> [!IMPORTANT]
>
> **`CI/CD` 不是"自动化工具"，而是 `SDK` 开发者对使用者的承诺兑现机制**。没有 `CI/CD` 的 `SDK`，就像没有质检的生产线——你也许能做出好产品，但你没法让客户相信你每次都能做出好产品。
>
> 这篇文章，就是把这句话落到 [`smart-dbc`](https://github.com/shilic/smart-dbc) 上的完整实践——从"手动改版本号、手动打包、手动上传"，到"合并一个 PR 就全自动发布"。

<!-- more -->

## 一、🔭 为什么 `SDK` 尤其需要 `CI/CD`

普通业务代码的一个 `bug`，影响一个功能；`SDK` 的一个 `bug`，影响所有下游项目。这个不对称，决定了 `SDK` 的质量标准必须更高。

上一篇文章我拿同星 `TSMaster API` 举过反例：2023 年的函数 `tsfifo_receive_can_message_list`，到了 2025 年直接被删除、替换成 `tsfifo_receive_can_msgs_list`，参数类型也乱改。结果所有依赖它的上位机全部瘫痪。

**同星的问题不是技术问题，是工程流程问题。** 如果有 `CI/CD`：

1. **兼容性测试**：会在合并前发现 `tsfifo_receive_can_message_list` 被删除，`CI` 直接失败，逼你恢复旧函数或升主版本。
2. **自动版本管理**：破坏性变更自动触发主版本号 +1，使用者看到 `2.0.0` 就知道"这次升级要改代码"。
3. **自动发布**：发布的 `DLL` 版本和文档版本一致，不会出现"手册写新版、用户装旧版"的混乱。

`CI/CD` 解决的，就是这三件事。

## 二、🏗 整体架构：`CI` 门禁 + `CD` 自动发布

整套流程分两部分，各司其职：

```
写代码 → 提交(feat/fix) → push 到 master
        ↓
CI 质量门禁（编译 + 单元测试 + 静态扫描）
        ↓
release-please 自动开 release PR（内含新版本号 + CHANGELOG）
        ↓
你合并这个 release PR          ← 唯一的手动动作
        ↓
自动打 vX.Y.Z tag + 创建 GitHub Release
        ↓
触发 publish，发布到 Maven Central + GitHub Packages
```

- **`CI`（持续集成）**：每次 push / PR 跑质量门禁，拦截不合规的提交。理想情况包括单元测试覆盖率 ≥ 80%、静态扫描（detekt）、依赖漏洞扫描、二进制兼容性检查（japicmp）。
- **`CD`（持续交付）**：根据 `commit message` 自动决定版本号、生成 `CHANGELOG`、打 `tag`，并发布到包仓库。

> [!NOTE]
>
> **一句话定义**：`CI` 保证代码质量，`CD` 保证交付可靠。`CD` 建立在 `CI` 之上——`CI` 没过，就不应该进入 `CD`。

### 触发条件的关键细节

`CD` 的发布动作，只在**合并 `release PR`** 的那一刻触发。这里是最容易误解的地方：

- **合并 `release-please` 自动开的那个 `PR`**（标题形如 `chore(master): release x.y.z`）→ 触发发布。
- **合并普通分支**（例如 `dev` → `master`）→ 只同步代码，**不触发发布**。

判断标准：发布 `job` 的触发条件是 `release_created == 'true'`，只有合并 release PR 那一刻才会变成 `true`。

## 三、🚀 `CD` 的核心：`release-please`

`release-please` 是 `Google` 开源的发布自动化工具，专门解决版本号和 `CHANGELOG` 的管理问题。它基于 **Conventional Commits（约定式提交）**，从 `commit message` 推断版本号变化：

| Commit 类型 | 版本号变化 | 示例 |
|---|---|---|
| `fix:` | 补丁 +1 | `1.2.3 → 1.2.4` |
| `feat:` | 次版本 +1 | `1.2.3 → 1.3.0` |
| `feat!:` / `BREAKING CHANGE:` | 主版本 +1 | `1.2.3 → 2.0.0` |

其余类型（`docs:`、`chore:`、`refactor:`、`ci:` 等）**不触发版本号变化**。

### 版本号从哪来

关键点：版本号**不再手写**，而是委托给 `release-please`。它通过一个注释标记定位版本号所在的行：

```kotlin
// build.gradle.kts
version = "1.1.3" // x-release-please-version
```

`release-please` 运行时读取提交历史，按 `Conventional Commits` 决定新版本号，然后自动改写这行、更新 manifest、生成 `CHANGELOG.md`、打 `tag`。

### 工作流

```yaml
# .github/workflows/release.yml（节选）
on:
  push:
    branches: [ master ]

permissions:
  contents: write
  pull-requests: write
  packages: write          # 发布 GitHub Packages 需要

jobs:
  release-please:
    outputs:
      release_created: ${{ steps.release.outputs.release_created }}
    steps:
      - uses: googleapis/release-please-action@v4
        with:
          token: ${{ secrets.GITHUB_TOKEN }}
          config-file: release-please-config.json
          manifest-file: release-please-manifest.json

  publish:
    needs: release-please
    if: needs.release-please.outputs.release_created == 'true'
    # ... 发布到 Maven Central + GitHub Packages
```

> [!TIP]
>
> **`release_created` 是整条发布链的开关**。只有当 release PR 被合并、release-please 真正创建了 release（打 tag）时，它才会变成 `true`，进而触发 `publish` job。

## 四、📦 发布到 `Maven Central` + `GitHub Packages`

`smart-dbc` 同时发布到两个仓库：

| 仓库 | 用途 | 特点 |
|---|---|---|
| Maven Central | 公众依赖 | 需要 `GPG` 签名 + Sonatype 凭证，有暂存区 |
| GitHub Packages | 内部/镜像 | 用 `GITHUB_TOKEN` 即可，无暂存，上传即发布 |

### GPG 签名

Maven Central 强制要求 `GPG` 签名。通过环境变量把私钥和密码注入到 Gradle：

```yaml
- name: 发布到 Maven Central
  run: ./gradlew publishToMavenCentral
  env:
    ORG_GRADLE_PROJECT_mavenCentralUsername: ${{ secrets.MAVEN_CENTRAL_USERNAME }}
    ORG_GRADLE_PROJECT_mavenCentralPassword: ${{ secrets.MAVEN_CENTRAL_PASSWORD }}
    ORG_GRADLE_PROJECT_signingInMemoryKey: ${{ secrets.GPG_PRIVATE_KEY }}
    ORG_GRADLE_PROJECT_signingInMemoryKeyPassword: ${{ secrets.GPG_PASSPHRASE }}
```

### 一个容易忽略的细节

`build.gradle.kts` 里的 `signAllPublications()` 签的是**所有 publication**。这意味着**发布到 GitHub Packages 的那一步，也会触发签名任务**，所以 GitHub Packages 步骤同样要带上签名环境变量，否则会报 `no configured signatory`。

## 五、🕳 踩坑记录：从 0 到 1 的十几个坑

理论很美好，落地全是坑。下面是我在 `smart-dbc` 上真实踩过的坑，按报错归类。**这些坑没有一个是网上能直接搜到的，全是时间和耐心换来的。**

### 坑 1：`gradlew` 可执行权限丢失

```
./gradlew: Permission denied
Error: Process completed with exit code 126.
```

Windows 上开发，`gradlew` 这个 shell 脚本在 git 里丢了 `+x` 可执行位。Linux runner 执行 `./gradlew` 时被拒。

**解法**：在 workflow 里加一步防御，运行时强制 `chmod +x gradlew`，彻底绕开 git 权限位的问题。

### 坑 2：`gradle-wrapper.jar` 被 `.gitignore` 忽略

```
Could not find or load main class org.gradle.wrapper.GradleWrapperMain
```

`.gitignore` 里的 `*.jar` 规则把 `gradle-wrapper.jar` 也忽略了，导致这个 jar 从没进过 git。runner 上 checkout 出来没有它，`gradlew` 直接报错。

**解法**：在 `*.jar` 之后加 `!gradle/wrapper/gradle-wrapper.jar`（注意：gitignore 是"最后匹配的规则生效"，所以例外必须写在 `*.jar` 后面）。

### 坑 3：`GPG` 私钥格式

```
Could not read PGP secret key
```

这个最隐蔽。`gradle.properties` 里存私钥用的是 Java Properties 的 `\n\` 转义格式：

```
signingInMemoryKey=\
-----BEGIN PGP PRIVATE KEY BLOCK-----\n\
...
```

如果你把这段**带 `\n` 转义的文本**直接复制进 GitHub Secret，secret 里存的就是字面的 `\n`，私钥就坏了。

**解法**：不要从 `gradle.properties` 复制，用命令重新导出真实换行的 armored 文本：

```bash
gpg --armor --export-secret-keys <你的KEY_ID>
```

### 坑 4：发布任务缺签名环境变量

```
Cannot perform signing task ':signMavenPublication' because it has no configured signatory
```

如第四节所说，`signAllPublications()` 签所有 publication，GitHub Packages 步骤也得带签名环境变量。

### 坑 5：`packages: write` 权限缺失

```
Could not PUT '.../smart-dbc-1.1.3.jar'. Received status code 403 from server: Forbidden
```

workflow 的 `permissions` 只写了 `contents: write` 和 `pull-requests: write`，漏了发布 GitHub Packages 需要的 `packages: write`。

### 坑 6：Maven Central 只暂存、不发布

`publishToMavenCentral` 只是把包**上传到 Sonatype Central Portal 的暂存区**，不会自动正式发布。结果是"命令成功了，但 Maven Central 上找不到包"。

**解法**：改用 `publishAndReleaseToMavenCentral`（自动 close+release），或去 central.sonatype.com 手动点 Publish。

### 坑 7：`Re-run` 用的是旧 workflow

发布失败后点 "Re-run failed jobs"，还是会报同样的错。因为 GitHub 的 "Re-run" 用的是**那次运行对应的旧 workflow 文件**，不含你后来的修复。

**解法**：要补发就本地手动跑 `./gradlew publish...`，或者 push 新提交触发新 run。

### 坑 8：`dev` 和 `master` 的分支错位

workflow 触发条件是 `push` 到 `master`。你在 `dev` 上的提交**不会触发 CI/CD**。这个坑最磨人——"本地明明改了，CI 上却没生效"。

**解法**：凡是要发版、要跑 CI 的改动，commit 后及时合并到 `master`。

### 坑 9：GitHub Packages 版本不可覆盖

GitHub Packages 的版本是**不可变**的——同一个版本号一旦发布，就无法覆盖或删除。发失败后想重发同版本，会一直 403。

**解法**：要么删掉那个残缺版本再重发，要么直接放弃，等下一个版本号。

## 总结

回到《SDK的设计哲学》第八章那句话——**`CI/CD` 是 `SDK` 开发者对使用者的承诺兑现机制**。

这套流程真正解决的问题，不是"省了几分钟手动打包的时间"，而是：

- **版本号不再手写**，杜绝人为错误，`fix`/`feat`/`BREAKING CHANGE` 自动映射补丁/次版本/主版本。
- **`CHANGELOG` 不再补写**，从 commit message 自动生成。
- **每一次发布都经过 CI 门禁**，质量不过关的代码到不了使用者手里。
- **每一个版本都可追溯**，tag、release、包，三者一一对应。

落地过程确实踩了不少坑——`gradlew` 权限、`wrapper jar` 被忽略、`GPG` 私钥格式、`packages` 权限、暂存区不自动发布……这些坑的共同点，是它们都不在"官方文档的 happy path"里。

但把这些坑踩平之后，收获的是一个**真正可信的发布管线**：合并一个 PR，剩下的全自动。这正是 `SDK` 该有的样子——**把使用者的信任，用流程一点点攒出来，而不是靠嘴说。**
