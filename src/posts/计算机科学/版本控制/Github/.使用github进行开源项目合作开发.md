# 使用github进行开源项目合作开发

GitHub 上的开源协作有一套成熟且被广泛遵循的玩法，核心是两个模型：**fork-and-pull**（你没写权限时用，开源主流）和**共享仓库模型**（核心维护者直接在同一个仓库开分支）。下面按"贡献者怎么做"和"维护者怎么组织"两条线给你拆清楚。

## 🥇 贡献者视角：从零提一个 PR

开源贡献的标准姿势是 **Fork + Pull Request**，整套流程如下：

**1. 先读规则，再动手**

打开仓库先看这几个文件，能省掉 90% 的返工：

- `README.md`：项目是干嘛的、怎么跑起来
- `CONTRIBUTING.md`：贡献指南（分支命名、测试要求、commit 规范）
- `CODE_OF_CONDUCT.md`：社区行为规范
- `LICENSE`：许可证类型

找不到 `CONTRIBUTING.md`？去看 Issue 列表里别人怎么提的，或者翻最近合并的 PR 模仿它们的格式。

**2. Fork & Clone**

```bash
# 在 GitHub 点 Fork 按钮，把仓库复制到你的账号下
git clone https://github.com/你的用户名/项目名.git
cd 项目名
# 添加上游远程，方便后续同步
git remote add upstream https://github.com/原作者/项目名.git
```

**3. 开一个功能分支**

```bash
git checkout -b fix/typo-in-readme
```

⚠️ 永远不要在 `main` 上直接改。每个功能/修复单独一个分支，分支名要有意义。

**4. 小步提交**

```bash
git add .
git commit -m "fix: 修正 README 中的拼写错误"
```

好的 commit message vs 坏的：

- ✅ `fix: correct typo in README`、`feat: add OAuth login`
- ❌ `更新了文件`、`修复bug`

**5. 推到自己 fork 并发 PR**

```bash
git push origin fix/typo-in-readme
```

然后去 GitHub 页面点 **Compare & pull request**，填清楚：

- **标题**：一句话说清改了什么
- **描述**：为什么改、怎么改的、如何测试
- **关联 Issue**：用 `Closes #123` 或 `#123` 关联相关 issue

发 PR 前确保本地测试通过，提交后盯紧 PR 下方的 **CI 状态**（GitHub Actions 会自动跑测试和 lint），全绿才可能被合并。

**6. 同步上游更新**

如果你的分支落后了：

```bash
git fetch upstream
git rebase upstream/main   # 或 merge
```

**新手建议**：从 `good first issue` 标签或文档/拼写类小问题起步，别一上来就重构核心模块，维护者大概率不会接。

## 🛡️ 维护者视角：把项目治理好

如果你是自己开源项目的 owner，下面是让协作可持续的关键设置。

### 必备的社区健康文件

GitHub 的 Community Profile 检查清单会看这些文件是否存在：

| 文件                               | 作用                                                  |
| ---------------------------------- | ----------------------------------------------------- |
| `README.md`                        | 项目门面，60 秒内让人看懂"是什么、为什么用、怎么上手" |
| `LICENSE`                          | 法律基础，决定别人能怎么用你的代码                    |
| `CODE_OF_CONDUCT.md`               | 社区行为准则                                          |
| `CONTRIBUTING.md`                  | 贡献指南：开发环境搭建、测试要求、PR 规范             |
| `.github/ISSUE_TEMPLATE/`          | Issue 模板（bug / feature / doc / question）          |
| `.github/PULL_REQUEST_TEMPLATE.md` | PR 模板                                               |

一个典型的 PR 模板长这样：

```markdown
## 变更类型
- [ ] Bug 修复
- [ ] 新功能
- [ ] 文档更新

## 变更描述

## 相关 Issue
Closes #

## 检查清单
- [ ] 代码已自测
- [ ] 文档已更新
- [ ] 测试用例已添加
```

### 分支保护与 CODEOWNERS

在仓库 **Settings → Branches** 给 `main` 设保护规则：

- 禁止直接 push
- 要求 PR 审查通过后才能合并
- 要求状态检查（CI）通过

再用 `CODEOWNERS` 文件自动指派审查人（放在 `.github/`、`root` 或 `docs/` 目录下）：

```text
# .github/CODEOWNERS
*       @global-owner1 @global-owner2
*.js    @js-owner
docs/*  @docs-team
/build/logs/ @doctocat
```

效果：有人提 PR 改了对应文件，**代码所有者会被自动请求审查**；配合分支保护规则，还可以强制要求代码所有者批准才能合并。

### CI/CD 自动化

公开仓库可以**免费使用 GitHub Actions**。建议在每次 push 和 PR 时自动跑：

- 单元测试、集成测试
- Lint / 代码格式检查
- 构建产物

> 💡 Actions 安全要点（2025-2026 年供应链攻击高发）：
>
> - 第三方 action 要 pin 到完整 commit SHA，不要用 `@main`
> - `GITHUB_TOKEN` 默认设最小权限（read-only），按需提升
> - 不要把 `pull_request_target` 搭配 checkout PR head 代码使用
> - 密钥一律走 `secrets`，绝不硬编码

### Issue 与项目看板

- 用标签体系分类：`bug` / `enhancement` / `priority-high` / `area-core` 等
- 用 **GitHub Projects** 做看板，可视化流转状态
- 里程碑（Milestone）拆成 1-2 周可完成的小块，每块都要有可交付物

## 🤝 协作中的软规则

这部分比工具更重要：

- **一个 PR 只做一件事**：便于审查，500 行以内最佳
- **分支短命**：一两周内合并，拖久了和 main 分歧越来越大
- **审查评论用提问句式**："这里为什么不这样做？" 比 "这样不对" 更容易让人接受
- **自己不能 approve 自己的 PR**：至少一人批准才能合
- **CI 不过的 PR 不予合并**
- **沟通主动**：被要求修改很正常，别往心里去；延迟或阻塞及时在 Issue/PR 里说一声

------

## 一个最小可行的工作流总结

**贡献者**：

```
Fork → Clone → 建分支 → 改代码 → 小步提交 → Push → 发 PR → 盯 CI → 回应审查
```

**维护者**：

```
设分支保护 → 配 CODEOWNERS → 写贡献指南和模板 → 接 CI → 用 Issues/Projects 跟踪 → 审 PR 并合并
```

按这套来，一个人提 PR 和十个人协同开发都不会乱。
